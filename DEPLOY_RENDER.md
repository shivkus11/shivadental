# Deploy the Dental Clinic Management System to Render

The repository root must remain the Render root directory because the Express server serves the sibling `web/` folder.

## 1. Push the project to GitHub

Create a new private GitHub repository, extract this ZIP, and push the entire `DentalClinicManagementSystem` folder contents to the repository. Do not commit `backend/.env`, database passwords, JWT secrets or Cloudflare R2 credentials.

## 2. Create Render PostgreSQL

1. In Render, choose **New + -> PostgreSQL**.
2. Name it, for example `dental-clinic-db`.
3. Choose a region. Use the same region for the web service in the next step.
4. Create the database and wait until it is available.
5. Open the database's **Connect** section and copy its **Internal Database URL**.

Use the internal URL for a Render-hosted service in the same region. Render documents internal connections as private-network connections; external database connections require TLS. See the official database guide: https://render.com/docs/postgresql-creating-connecting

## 3. Create the Render web service

1. Choose **New + -> Web Service** and connect the GitHub repository.
2. Set **Root Directory** to blank / repository root.
3. Select **Node** as the runtime.
4. Set **Build Command**:

```bash
cd backend && npm install
```

5. Set **Start Command**:

```bash
cd backend && npm run migrate && npm start
```

The migration command runs when the service starts, after its database connection is available. The schema statements use `IF NOT EXISTS`, so restarting the service is safe for this initial schema.

6. Set **Health Check Path** to `/api/health` if the field is available.
7. Choose a service plan and create the service.

The server listens on Render's `PORT` environment variable and binds to `0.0.0.0`.

## 4. Set web-service environment variables

Open the web service's **Environment** page and add:

| Key | Value |
|---|---|
| `NODE_ENV` | `production` |
| `DATABASE_URL` | Internal Database URL copied from your Render Postgres database |
| `PGSSL` | `false` when using the same-region internal URL |
| `JWT_SECRET` | A unique random secret, at least 32 characters |
| `JWT_EXPIRES_IN` | `12h` |
| `R2_ACCOUNT_ID` | Your Cloudflare Account ID |
| `R2_ACCESS_KEY_ID` | R2 access key ID |
| `R2_SECRET_ACCESS_KEY` | R2 secret access key |
| `R2_BUCKET` | Your R2 bucket name |
| `R2_ENDPOINT` | `https://YOUR_ACCOUNT_ID.r2.cloudflarestorage.com` |
| `R2_PRESIGN_SECONDS` | `300` |
| `MAX_UPLOAD_BYTES` | `26214400` |
| `CORS_ORIGINS` | `https://YOUR-SERVICE.onrender.com` |

Replace the example service URL with the actual HTTPS URL Render assigns to the web service. If you use a custom domain, include that origin too. Save the values and deploy/redeploy.

Generate a JWT secret on your computer with:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Do not reuse the same secret between environments. Do not expose R2 credentials in Android or web JavaScript.

## 5. Configure Cloudflare R2

1. In Cloudflare, create a private R2 bucket, for example `dental-clinic-files`.
2. Create an R2 API token with object read/write permission scoped to this bucket. Copy the Access Key ID and Secret Access Key into Render environment variables.
3. Keep public bucket access disabled. This application uses short-lived presigned URLs generated by the backend.
4. In the bucket's CORS settings, allow the web-service origin so the browser can upload directly to the bucket. Example configuration:

```json
[
  {
    "AllowedOrigins": [
      "https://YOUR-SERVICE.onrender.com"
    ],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

For local browser testing, add `http://localhost:3000` to `AllowedOrigins` as well. This is the bucket's CORS configuration; `CORS_ORIGINS` in the Render environment controls requests to your Express API. Cloudflare's current presigned URL guide documents the R2 S3 endpoint, `region: "auto"`, and temporary GET/PUT URLs: https://developers.cloudflare.com/r2/api/s3/presigned-urls/

## 6. Create the first admin account

After the Render service is deployed, run the account-creation script from your computer using the database's **External Database URL** (not the internal URL). In `backend/.env`, temporarily set:

```env
DATABASE_URL=PASTE_RENDER_EXTERNAL_DATABASE_URL_HERE
PGSSL=true
```

Then from the `backend` folder run:

```bash
npm install
npm run create-user -- --email admin@example.com --password "UseAUniqueStrongPassword!" --role admin --name "Clinic Admin"
```

The external Render database URL requires TLS; keep `PGSSL=true` for this one-off local connection. After creating the admin, remove the external database URL from your local `.env` and restore local settings. Never paste a database URL into GitHub or share it.

## 7. Verify deployment

Open:

- `https://YOUR-SERVICE.onrender.com/api/health` - should return `status: ok` and `database: connected`.
- `https://YOUR-SERVICE.onrender.com` - staff / doctor sign-in page.

Sign in with the admin account and create a test patient. Register a separate patient account in the Android app. Upload a test image and verify it appears in R2 and in the patient record.

## 8. Point Android at Render

On your computer:

```powershell
cd android
.\gradlew.bat assembleDebug -PAPI_BASE_URL=https://YOUR-SERVICE.onrender.com/
```

The APK is in `app/build/outputs/apk/debug/app-debug.apk`. Install it on an Android test device. The Android app calls the HTTPS Render API; it does not connect directly to PostgreSQL or hold R2 credentials.

## Deployment notes

- Render and Cloudflare service availability, billing and plan limits can change; check the current dashboard before choosing production plans.
- Keep the Render web service and Render Postgres database in the same region and use the internal database URL.
- Configure automated database backups and test restore procedures before any real clinic use.
- A free web service may sleep or have resource limits; check Render's current plan limitations. The database plan is separate from the web service plan.
